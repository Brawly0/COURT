1. What the game is

CASE CLOSED is a 4–8 player courtroom-detective game. A procedurally generated crime, a 15-minute investigation, an 8-minute trial before a deterministic AI judge, and a truth reveal at the end.

The defining constraint, which drives nearly every decision in this log: the game is about asymmetric knowledge. The defendant knows whether they did it. Nobody else does. Players reconstruct the truth by physically moving around a building, searching for records, and talking to each other. That means secrecy is not a feature bolted on later — it is the thing the architecture has to protect at every layer.

Pre-existing work (not built in this log)

ComponentState
src/CaseClosed.TruthEnginePure C# case generator. netstandard2.1, zero dependencies, own PCG32 RNG. 18 tests.
Assets/Plugins/CaseClosed.TruthEngine.dllCompiled engine, already dropped into Unity.
docs/MAP_DESIGN.mdLevel design doc defining the run structure and roles.
Why this matters: the generator answers "what happened?" Unity answers "where can players find out?" These were kept strictly separate throughout. The generator was never modified.

2. Tooling — the Unity/Claude bridge

Work began by connecting Claude Code to the Unity Editor so changes could be made and verified without manual round-trips.

Two bridges ended up available: Unity's own local relay (unity MCP), and the third-party AI Game Developer plugin (IvanMurzak/Unity-MCP) from a YouTube tutorial.

Decision: the plugin defaulted to Cloud mode, routing scene data through ai-game.dev and requiring an OAuth login. Switched it to Custom mode, which runs gamedev-mcp-server.exe on localhost:24718 — no third-party routing, no account. The plugin's config had to be flipped on disk and a domain reload forced before it took effect.

3. Milestone 1 — Third-person player prototype

GOAL: spawn a character, walk, run, sprint, jump, camera follows, animations work

What existed, and what was left alone

The project already had FirstPersonController.cs wired into a networked player prefab, with the old courthouse calibrated against its speeds. It was not modified. The new third-person system was built alongside it.

Components created

PlayerMovementSpeed, gravity, slopes, jump, ground detection, turning.

Why input is isolated: when multiplayer arrives, a remote player's inputs get written into the same fields from the network instead of from a keyboard, and PlayerMovement never has to change. This one decision made Milestone 2 straightforward.

Character and animation

A blocky low-poly human built entirely from Unity primitives in an editor script — head, torso, arms, legs, hands, feet, simple face, suit. Seven animation clips (Idle, Walk, Run, Sprint, Jump, Fall, Land) generated procedurally as keyframed limb rotations, driven by a blend tree on measured velocity. No imported art.

4. Milestone 2 — Multiplayer foundation

GOAL: two players connect, see each other move, jump, animate; handle disconnects

Technology

Netcode for GameObjects 2.13.1, already in the project. Owner-authoritative: each player simulates their own character and broadcasts the result.

What runs where

MachineRuns
HostServer + a player. Relays traffic, owns spawning.
Your own characterInput, movement, camera, animation.
Someone else's characterNothing but presentation — a puppet moved by network data.
Reused hard-won knowledge: a comment in the project's existing NetPlayer.cs read "a live CharacterController stomps external transform writes, freezing remote copies at spawn." That was from an earlier "Fix frozen remote players" commit. Remote characters therefore get their CharacterController disabled.

Animation replication

Animations are not sent as clips. Four small values cross the wire — speed, vertical speed, grounded, movement state — and every machine runs the same Animator Controller off them.

Why: a few bytes per tick instead of a stream of animation state, and remote characters blend Idle→Walk→Run→Sprint using the identical state machine, so they cannot drift out of sync with what the body is doing.

Verified with two real processes

remote states seen: Walk, Run, Sprint, Jump, Fall, Land
remote leg swing 111.4 deg (Sprint clip authored at 56 => 112)
disconnect: "client 1 left", host continued; 0 exceptions

5. Milestone 3 — Proximity voice chat

GOAL: hear nearby players, quieter with distance, silent beyond range

Technology decision

Built on NGO itself, not Vivox.

Why not Vivox (the usual answer): it requires a Unity Gaming Services project, dashboard linking and credentials — account setup that would have blocked the milestone entirely, plus a second network stack alongside NGO. The cost of not using it is real and was stated up front: no echo cancellation, no noise suppression, no AGC.

The audio path

Microphone -> 16 kHz mono -> G.711 mu-law -> 20 ms frames (320 bytes)
   -> ServerRpc -> host measures distance per listener
   -> ClientRpc to those in range only
   -> jitter buffer -> streaming AudioClip -> AudioSource ON THE SPEAKER'S BODY
Codec measured SNR36.6 dB (telephone quality is ~38 dB)
Compression4:1 versus float PCM
Bitrate~128 kbit/s per active speaker
Two-layer attenuation. The server drops frames for listeners beyond max range — that is the hard cutoff, and means a modified client cannot listen in from across the map because those packets were never sent. Within range, the AudioSource sits on the speaker's character at spatialBlend = 1, so distance and direction come free.

Verified across processes

dist= 8.2m  audioArriving=True   level=0.248
dist=14.8m  audioArriving=True   level=0.250
dist=28.2m  audioArriving=False  level=0.000
dist=72.2m  audioArriving=False  level=0.000

6. Milestone 4 — Voice occlusion + secrecy fix

GOAL: walls should block voice

Distance alone meant a player two metres away through a sealed courtroom wall was as loud as one standing next to you. For COURT that is worse than wrong — "can they hear me from in there" is the actual game.

Occlusion, two layers again

  • Server (authoritative): walls shrink how far a voice carries. A modified client cannot hear through a wall, because those packets are never sent.
  • Client (presentation): volume drop plus a low-pass filter.
Why the low-pass matters: volume alone just sounds far away. Losing the high frequencies is what reads as "through a door". Interpolated in log space, because perceived brightness is logarithmic, and smoothed over 0.18 s so doorways fade rather than pop.
open floor, clear line        blockers=0   occlusion=0.00   carries 21.0 m
through one corridor wall     blockers=1   occlusion=0.33   carries 16.5 m
through both corridor walls   blockers=2   occlusion=0.67   carries 11.9 m

One wall muffles rather than silences — deliberately, since overhearing a muffled argument through a courtroom door is a mechanic worth having.

Leak found and closed. IsSpeaking was a NetworkVariable readable by everyone, so a client knew a player across the map was talking even though the server had correctly refused them the audio. In a game built on eavesdropping that is exactly the information you must not leak. It is now derived from audio actually received — zero bandwidth, and it cannot lie.

Before: dist=72.2m speaking=True  →  After: dist=72.1m speaking=False

7. Milestone 5 — Greybox courthouse

GOAL: Archive, Witness Lounge, Courtroom around a central Atrium

The previous v2.3 courthouse was removed at the user's request (all recoverable from commit c272023), along with the first-person player and the scripts welded to it.

The plan is a hub and three spokes

                    COURTROOM
                        |            (40 m from atrium centre)
      ARCHIVE ------ ATRIUM ------ WITNESS LOUNGE
    (40 m west)                      (40 m east)
Every room is 40 m from the middle — about 9.3 s at the controller's 4.3 m/s run speed, inside the 8–12 s target. Any two rooms are 80 m apart via the atrium (~18.6 s), under the 20 s ceiling.

Everything routes through the atrium on purpose. There are no shortcuts between wings, so crossing the building means passing through the one space where everyone else is. That is where chance encounters and overheard conversations happen. A ring corridor would be kinder to navigate and would kill the game.
RoomContents and intent
ArchiveShelf aisles chop it into lanes, so two players searching can be metres apart and neither see nor clearly hear each other.
Witness LoungeOpen waiting area plus an interview nook behind a partition — the first place you can hold a conversation others cannot quite hear.
CourtroomJudge dais, witness stand, opposed counsel tables, bar, gallery benches. Positions only, no trial logic.
AtriumPillars break sightlines; reception desk as a landmark.

RoomVolume + GreyboxDebugHud (F3) record real travel times during play rather than calculating them from distances.

8. Milestone 6 — Case generator integration

GOAL: host generates a case, owns the truth, clients get only what they may know
Correction made during this milestone. The generator was initially wired in as a local package. That was wrong — a current, git-tracked CaseClosed.TruthEngine.dll already sat in Assets/Plugins. The compiler caught it (CS1704: assembly already imported); the package was reverted and the existing DLL used.

The four data layers

TypeHoldsWho sees it
CompleteCaseTruthEverything: perpetrator, occupancy, corruptions, proof chainHost only
PublicCaseInfoTitle, crime, briefing, cast, durationEveryone
PlayerCaseViewRole, private briefing, permitted facts, guilt (defendant only)One player
DeveloperCaseDebugViewEverything, formattedHost, dev builds, behind F2
Protection is structural, not procedural. CompleteCaseTruth is a managed class that does not implement INetworkSerializable and contains dictionaries and jagged arrays — so SomethingClientRpc(truth) is a compile error. ActiveCaseManager has no NetworkObject, so it cannot replicate even by accident. There is no permission to misconfigure.

The guilt bit is sent as false to non-defendants regardless of the truth, so the packet carries no signal either way.

Bug caught by the audit: FixedString128Bytes is sized in bytes, but the truncation helper counted characters — and the generator's prose contains em-dashes (3 UTF-8 bytes each). A 124-character string could be 130 bytes and throw. Fixed to a byte budget.

9. Milestone 7 — Role assignment

GOAL: server-authoritative roles, exactly one Defendant, safe late join

Roles came from the project's own docs/MAP_DESIGN.md rather than being invented:

LOBBY      Roles dealt. Defendant learns the truth, alone, on his card.
BRIEFING   Both teams enter their own office. Prosecution gets 1 forensic
           fact. Defense gets nothing and has to ask their client.
RoleTeamUnique?
DefendantDefenseYes — dealt once per case, never re-dealt
Defense AttorneyDefenseYes
ProsecutorProsecutionYes
InvestigatorProsecutionNo — repeatable seat

The judge is the deterministic AI, never a player.

Roles are public; guilt is not. In a courtroom you can see who is prosecuting. Hiding it would buy no secrecy and would make name tags and office doors impossible. Guilt travels on a separate channel to one player. Keeping them apart stops a future feature widening the roster and leaking the mystery.
A departed Defendant is not replaced. Promoting someone mid-case would hand a stranger the answer to the mystery. The seat goes vacant, DefendantMissing flips true, and the trial system decides between in-absentia (which the design doc already names) and a redeal.

Dealt from the case seed using the project's own PCG32, with client ids sorted before shuffling — NGO reports connections in arbitrary order, so without sorting "deterministic" would be a lie.

10. Milestone 8 — Briefings and ready flow

GOAL: every player gets role, team, public info, private briefing, and a Ready button

A match-level state machine kept separate from the case lifecycle:

LobbyReady -> AssigningRoles -> GeneratingCase -> DistributingBriefings
           -> WaitingForPlayers -> PreInvestigationReady
Why separate: CaseLifecycleState answers "does a generated case exist and has it been distributed" — a data question. MatchPhase answers "what are the humans doing" — a session question. Merging them would mean regenerating a case rewinds the lobby.

Readiness

SubmitReadyServerRpc takes no client id — NGO supplies the sender, so marking another player ready is unrepresentable rather than merely validated. A server-side HashSet makes duplicates idempotent; disconnect withdraws readiness.

A real leak, found by strengthening a weak test. The first "hides the perpetrator" check ran on a guilty case — where the perpetrator is the defendant, so it passed vacuously. Re-running against an innocent case exposed that the Prosecutor's opening fact was ProofFacts[0] — and the proof chain is precisely what implicates the real culprit. The Prosecutor was being handed the answer at the briefing screen.

Fix: sourced from the defendant's baggage instead — true, discoverable, about the defendant, and never naming the culprit. Better design, not just a patch: baggage is why the state charged them.

Verified with four processes

[Roles] Dealt — 1 Defendant, 1 Defense Attorney, 1 Prosecutor, 1 Investigator
phase: AssigningRoles -> GeneratingCase -> DistributingBriefings
       -> WaitingForPlayers -> PreInvestigationReady
Ready 1/4 -> 4/4 -> ALL PLAYERS READY

p0 DefenseAttorney/Defense    knowsGuilt=False guiltBit=False
p1 Investigator/Prosecution   knowsGuilt=False guiltBit=False
p2 Defendant/Defense          knowsGuilt=True  guiltBit=True
p3 Prosecutor/Prosecution     knowsGuilt=False guiltBit=False

11. Milestone 9 — Networked interaction system

GOAL: one reusable interaction contract for shelves, doors, terminals, the gavel

The contract

NetworkInteractable is an abstract base, not an interface.

Why a base class: the parts that must not vary — distance checks, the exclusivity lock, hold timing, release on disconnect — live in one place and cannot be forgotten by an implementer. An interface would let every future object re-invent locking, and one of them would get it wrong.

What a client may say

"I would like to interact with object 47." That is the entire vocabulary. No position, no result, no completion time. The server resolves the id through NGO's spawn table — a fabricated id resolves to nothing — measures distance itself, and runs its own clock.

Server validation order (cheapest first)

  1. Player exists and is spawned
  2. Player state allows interaction
  3. Target is available
  4. Not locked by another player
  5. Role/team permission
  6. Distance (measured server-side)
  7. Line of sight
  8. The object's own ServerValidate

Holds tick in the server's Update, re-running full validation every frame. Walking away, losing sight, or the object becoming unavailable cancels without the client's cooperation. The client is never asked how long it held the key.

Bug 1 — Unity script binding. Four MonoBehaviours were put in one file. The project already documents this in ClientNetworkTransform.cs: "Unity's script-to-prefab binding breaks for MonoBehaviours defined in a file named after a different class." Split into separate files.
Bug 2 — stuck asset import. InteractionNetworkController.cs was valid C#, had a unique GUID, and Unity refused to emit its type while reporting no error against the file. Forced reimport and recompile did not help. Deleting the asset and recreating it with a fresh GUID did. Worth remembering: if a type "doesn't exist" with no error against its file, that is the fix.
Bug 3 — the one that mattered: raycasting from the camera. COURT is third-person. The camera sits ~5 m behind the character (measured), and the probe range was 3.5 m — so the ray expired about a metre behind the player's own back and could never reach anything in front of them. Nothing was ever targetable; pressing E did nothing.

Fix: cast from the player's eyes, along the camera's facing. You reach for what you are looking at, from where you actually are. It also matches how the server measures distance, so the prompt cannot promise something the server then refuses.
Bug 4 — stale prefab. The interaction detector was added to the prefab builder, but only the scene builder had been re-run. The prefab was stale and the component simply was not on the player. Diagnostic output: detector on player : False.

Feedback added after "I can't tell if E did anything"

The crosshair became the confirmation: grows amber when something is targetable, punches white on press before the server answers, then flashes green on success or red on refusal. Plus a message when no session exists — that silence was indistinguishable from a bug.

12. Milestone 10 — Archive search and evidence discovery

GOAL: search Archive containers, discover real generated evidence, reach FOUND

Key inspection finding

The generator already answers the placement question. Every EvidenceItem carries a FoundAt string:

#ItemFoundAtArchive?
0{CrimeObject} (recovered)Impound cage, parking garageno
1Fingerprint card: …Lab tray (90s)no
2CCTV tape: …Security office consoleno
3Catering scheduleArchives, row 3yes
4Door log: {location}Archives, row 5yes
5Toxicology slip (Fractured only)Lab tray (120s)no
So categories were not invented. Unity reads the generator's own intent, which is what keeps fingerprints and stolen goats out of filing cabinets. Three gaps were flagged rather than smuggled in: no stable EvidenceId (derived as E-003 from list position), no type enum (parsed from FoundAt), and only 2 Archive-suitable items per case.

Secrecy of placement

The placement map is a plain Dictionary on ArchiveDirector — never a NetworkVariable, never an RPC parameter. ArchiveContainer has no contents field at all; it cannot leak what it does not know, and asks the director at completion.

Ten containers

Desk Drawer     1.5 s
Records Box     2.5 s
Filing Cabinet  3.0 s
Shelf Section   4.0 s

Junk is deliberately inert — no character names, no times, no locations. It must waste a player's time, never mislead them into an accusation the case cannot support.

Placement seeds from caseSeed XOR salt on a separate PCG32 stream from the case and the role deal, so reshuffling the Archive can never disturb either.

13. Milestone 11 — Physical evidence custody

GOAL: FOUND -> CARRIED -> DROPPED, and another player can pick it up

The central question, answered

The audit found the existing FOUND was knowledge, not custody — it recorded who learned it and had no notion of a physical object. So the two were split:

ShapeBehaviour
Knowledgea set of readers per itemonly ever grows
Custodya single field per itemexactly one location
That asymmetry does the work. Knowledge is a set, so several people can know the same thing and nobody forgets when they hand a folder over. Custody is one field, so duplication is unrepresentable — an item cannot be in a drawer and a hand, because there is nowhere to write the second location.

The loop

Discovery reveals a manila folder into the world, not into an invisible inventory — you know what the document says before you hold it. Carry limit is one. Carrying is not physics: the server owns who holds it, and every client draws it at that player's socket.

Drop (G) takes no position from the client — a client-chosen position could post evidence through a wall. Inspection (Tab) never shrinks: drop a folder and you still remember what it said.

On disconnect the carrier's item drops where they last stood and stays in play. Deleting it would silently remove a clue; returning it to its drawer would let a player hide evidence by pulling their network cable.

Bug — stale bodies. Rebuilding placement reset the evidence records but left folders from the previous case lying on the floor, still carrying ids that had just been reset — world objects with no backing record. Custody is now cleared whenever knowledge is.
Bug — evidence spawning into walls. Folders were revealed along container.transform.forward, but containers are built unrotated, so every forward is world +Z. The north row spawned its evidence at z=9.5, half a metre from the wall at z=10 — unreachable. Containers now carry an explicit RevealDirection.

Testing mistakes worth recording

  • A verdict reported PASS while the pickup never happened — the condition only checked state that was already true beforehand. Verdicts must require the transition, not the end state.
  • Hard-killing a process is not a disconnect — it sends nothing, so NGO waits out its ~30 s transport timeout. A graceful leave was needed to test the path. (This is also real production behaviour: a crashed player lingers ~30 s.)
  • Aiming the player is not aiming the camera — the camera rig keeps its own yaw, so tests had to place the player relative to where the camera actually looked.

16. Known limitations

AreaLimitation
MovementOwner-authoritative — a modified client could teleport or fly. Fine for prototype.
NetworkingDirect IP only. No NAT traversal until the Steam relay. No host migration.
NetworkingNo client-side prediction; remote players are ~1 tick in the past.
NetworkingClient ids are reassigned on reconnect — a returning player is a stranger to the roster.
VoiceNo echo cancellation, noise suppression or AGC. Headphones required.
Voice~128 kbit/s per speaker; Opus would cut that ~8x but needs a native plugin.
VoiceOcclusion is a single ray with no notion of an open door.

BriefingLate join after PreInvestigationReady does not rewind the phase.
ArchiveOnly 2 Archive-suitable items per case, so 8 of 10 containers are junk or empty.

BuildNo .NET SDK on the machine — the engine's 18 tests cannot run and the DLL cannot be rebuilt.

17. How to run and test

From the editor

Open Assets/Scenes/Courthouse.unity, press Play, click HOST.

Multiplayer

Build via Case Closed > Prototype > 4. Build Playground Player, then launch game/Build/Prototype/PlayerPrototype.exe two to four times. First window HOST, the rest JOIN 127.0.0.1.

Controls

WASD / mousemove / look
Shift / Ctrlsprint / walk
Space / Rjump / respawn
Einteract (hold for searches)
Gdrop carried evidence
Vpush to talk
M / Nmute / next microphone
Tabinspect evidence you know
F1 / F2 / F3 / F5movement / case debug / greybox / role

The full loop

  1. HOST, then F2 → START MATCH (deals roles, generates case, sends briefings)
  2. Each player reads their briefing and presses READY
  3. Walk west to the ARCHIVE
  4. Hold E on containers — most are empty or junk; two hold real evidence
  5. On a find, a manila folder appears. Press E to pick it up
  6. G to drop; another player can take it. Tab still shows what you read
